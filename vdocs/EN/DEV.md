# T4n OS Repository - Developer & Maintainer Guide

Welcome to the T4n OS repository infrastructure. This document is intended for developers and maintainers who want to build, package, and deploy software to the T4n OS repositories (`repo-glibc`).

## 1. Repository Structure

The repository is structured to separate build templates, binary outputs, and automation scripts.

```text
.
├── .github/workflows/       # CI/CD automation
│   ├── signature.sh         # Signs .xbps files using GitHub Secrets
│   ├── autogen-index.sh     # Generates index.html for directory browsing
│   └── autogen-json.sh      # Generates packages.json for the web frontend
├── <arch>/                  # Binary folders (x86_64, i686, aarch64, armv6l, armv7l)
│   ├── *.xbps               # Compiled binary packages
│   ├── *.xbps.sig2          # Cryptographic signature (generated by CI)
│   └── index.html           # Auto-generated directory listing
├── pkg-recipe/              # xbps-src build templates
│   └── <package_name>/
│       └── template
├── vtools/
│   └── auto.sh              # Local automation script (Build, Copy, Sync)
├── vdocs/                   # Documentation (EN/ID)
├── keys/                    # Public keys for signature verification
├── index.html               # Root directory listing (Auto-generated)
├── install.sh               # Repository installation script
├── README-ID.md
└── README.md
```

## 2. Prerequisites

Before contributing, ensure you have:

- Void Linux (or a compatible environment with `xbps-src` installed).
- Git and GitHub CLI (`gh`) installed and authenticated.
- Write/Owner access to the `T4n-Labs` GitHub organization repositories.

## 3. Supported Architectures

This repository **strictly supports 5 glibc architectures**:

| No | Architecture | Description |
|----|--------------|-------------|
| 1  | `x86_64`     | 64-bit PC (default for most desktops) |
| 2  | `armv6l`     | 32-bit ARM (Raspberry Pi 1, Zero) |
| 3  | `armv7l`     | 32-bit ARM (Raspberry Pi 2, 3 in 32-bit mode) |
| 4  | `aarch64`    | 64-bit ARM (Raspberry Pi 3/4 in 64-bit mode, Apple Silicon) |
| 5  | `i686`       | 32-bit PC (legacy) |

> ⚠️ **Note**: `musl` architectures (e.g., `x86_64-musl`) are **not supported** by this repository.

## 4. Local Workflow (`vtools/auto.sh`)

To speed up the packaging process, we provide `vtools/auto.sh`. This script handles environment setup, template synchronization, building, and file organization.

### A. Setup Environment
If you haven't cloned the `void-packages` build system yet, the script will do it for you and run the initial bootstrap.

```bash
./vtools/auto.sh --setup
# or
./vtools/auto.sh -s
```
> **Note**: Running `--build`, `--copy`, or `--sync` will also automatically trigger the setup if `void-packages` is missing.

### B. Template Synchronization
This feature copies the template from `pkg-recipe/<name>` to `void-packages/srcpkgs/<name>` without building. Useful for testing templates before building.

```bash
./vtools/auto.sh --sync
# or
./vtools/auto.sh -t
```

### C. Build Packages
The script reads the `archs` variable from your template to determine which architectures to build. It now features a **numbered menu** for easy selection.

```bash
./vtools/auto.sh --build
# or
./vtools/auto.sh -b
```

**Interactive Flow:**
1. Enter the package name (pkgname).
2. The template is automatically synced to `srcpkgs/`.
3. Select the target architecture using the numbered menu:
   ```text
   [1] x86_64
   [2] armv6l
   [3] armv7l
   [4] aarch64
   [5] i686
   [6] all (all supported architectures)
   ```
4. The default selection is automatically set to your host architecture.
5. Build begins (uses the `-a` flag for cross-compilation, never uses `-A`).

> 💡 **Tip**: You can select multiple architectures by separating them with commas (e.g., `1,3,5`).

### D. Copy Binaries to Repository
After building, move the compiled `.xbps` files from the build environment to the correct architecture folders in this repository.

```bash
./vtools/auto.sh --copy
# or
./vtools/auto.sh -c
```

**Automatic Old Version Cleanup**: The script automatically detects the package name and deletes older versions of the same package in the destination folder. For example, if `tpkg-1.1.0_1.x86_64.xbps` is copied, `tpkg-1.0_1.x86_64.xbps` will be automatically removed to save storage.

> **Default path**: `void-packages/hostdir/binpkgs`

## 5. Creating a New Package

Every package requires a build template located in `pkg-recipe/<package_name>/template`.

### Example Template (`pkg-recipe/zvc/template`):

```bash
pkgname=zvc
version=1.0_1
revision=1
archs="x86_64 i686 aarch64 armv6l armv7l"
short_desc="Void package compiler — build xbps from template"
maintainer="T4n Labs <admin@t4n.org>"
distributor="T4n Labs <admin@t4n.org>"
license="MIT"
homepage="https://github.com/T4n-Labs/zvc"
distfiles="https://github.com/T4n-Labs/zvc/archive/v${version%_*}.tar.gz"
checksum=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

do_build() {
    make
}

do_install() {
    make DESTDIR=$DESTDIR install
}
```

### `archs` Parsing Rules:
- **No `archs` defined** → Supports all 5 glibc architectures.
- **Standard token** (`x86_64`) → glibc only.
- **Token with `*`** (`x86_64*`) → The `*` is stripped; remains glibc only.
- **Token with `-musl`** (`x86_64-musl`) → The `-musl` suffix is stripped; becomes `x86_64`.

## 6. CI/CD Pipeline (GitHub Actions)

When you push changes to the `main` branch, GitHub Actions automatically triggers the following workflows:

### Triggers
The workflow only runs if changes are detected in:
- Architecture folders (`x86_64/`, `i686/`, `aarch64/`, `armv6l/`, `armv7l/`)
- `pkg-recipe/`
- `install.sh`
- `.github/workflows/**`

### Steps:
1. **Install tools** - Installs `xbps` and dependencies.
2. **Checkout repository** - Fetches code from the `main` branch.
3. **Index and sign packages** - Signs all `.xbps` files using the `SIGN_KEY` from GitHub Secrets.
4. **Generate index files** - Generates `index.html` for directory browsing.
5. **Generate packages.json** - Scans `.xbps` files and templates to generate metadata.
6. **Assemble site** - Gathers files to be served into the `_site` folder.
7. **Deploy to GitHub Pages** - Deploys the `_site` folder to GitHub Pages.

> 📝 **Note**: Generated files (repodata, `.sig2`, `packages.json`, `index.html`) are created in the `_site` folder and deployed directly to Pages. **They are NOT committed back to the repository.**

## 7. Frontend Integration (`script.js`)

The T4n OS web package search engine (`script.js`) relies on the generated `packages.json` files to display packages without hitting GitHub API rate limits.

### Data Loading Strategy
- **Primary Source**: Fetches `<arch>/packages.json` for all architectures in parallel (`Promise.allSettled`). If one fails, it is ignored; as long as one succeeds, it proceeds.
- **Fallback Mechanism**: If NO `packages.json` files are found, it falls back to the GitHub Trees API to parse `.xbps` filenames directly from the repository.

> ⚠️ **Warning**: The GitHub API is strictly rate-limited to 60 requests/hour/IP. A `403` error will display a rate-limit warning to the user. A `404` is treated as an empty repository, not an error.

### Required `packages.json` Schema

The `autogen-json.sh` script generates this file. If you are creating it manually or debugging, it must follow this exact structure:

```json
{
  "packages": [
    {
      "name": "zvc",
      "version": "1.0",
      "arch": "x86_64",
      "filename": "zvc-1.0_1.x86_64.xbps",
      "size": 184320,
      "desc": "Void package compiler — build xbps from template"
    }
  ]
}
```

**Notes**: 
- `name`, `version`, and `arch` are strictly required.
- `size` and `desc` (mapped from `short_desc`) are optional but highly recommended for the UI.
- `version` is without revision (`"1.0"`); the revision remains in the `filename` (`"zvc-1.0_1.x86_64.xbps"`).

## 8. Security & Secrets Management

To sign packages, the CI/CD pipeline requires a PEM-encoded RSA private key.

### Generating the Key (One-time setup)
```bash
ssh-keygen -t rsa -b 4096 -m PEM -f private.pem -N ""
```

### Adding to GitHub Secrets
Use the GitHub CLI to securely inject the key into the repository:
```bash
gh secret set SIGN_KEY -R T4n-Labs/repo-glibc < private.pem
```

> ️ **CRITICAL SECURITY WARNINGS**:
> - **NEVER** commit `private.pem` to the repository.
> - Ensure `private.pem` is explicitly listed in your `.gitignore`.
> - The public key (`private.pem.pub`) can be safely committed to the `keys/` directory for users to download and verify signatures.
> - The public key metadata is also automatically embedded into the `repodata` by `xbps-rindex`.

## 9. Deployment Checklist

Follow this checklist when adding a new package to the repository:

- [ ] Created `pkg-recipe/<name>/template` with correct `archs` and metadata.
- [ ] Ran `./vtools/auto.sh --sync` (optional, for template testing).
- [ ] Ran `./vtools/auto.sh --build` to build the package.
- [ ] Ran `./vtools/auto.sh --copy` to copy binaries and clean up old versions.
- [ ] Committed changes: `git add . && git commit -m "feat: add <name> <version>"`
- [ ] Pushed to GitHub: `git push`
- [ ] Verified GitHub Actions completed successfully (Check the "Actions" tab).
- [ ] Verified the package appears on the web search engine (`repo.t4nlabs.web.id/`).
- [ ] Verified the package can be installed via `xbps-install`.

## 10. Troubleshooting

### Build Fails
- Ensure the template has correct syntax.
- Check the `xbps-src` output logs for detailed errors.
- Ensure build dependencies are installed on the host.

### `packages.json` Not Created
- This file is only created during CI/CD; it is not committed to the repo.
- Check the GitHub Actions logs in the "Actions" tab for errors.
- Ensure the architecture folders (`x86_64/`, etc.) actually contain `.xbps` files.

### Old Versions Not Deleted
- Ensure you are running `./vtools/auto.sh --copy` (not copying files manually).
- The script automatically detects the package name and removes older versions.
