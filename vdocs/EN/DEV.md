# T4n OS Repository - Developer & Maintainer Guide

Welcome to the T4n OS repository infrastructure. This document is intended for developers and maintainers who want to build, package, and deploy software to the T4n OS repositories (`repo-glibc`).

## 1. Repository Structure

The repository is structured to separate build templates, binary outputs, and automation scripts.

```text
.
├── .github/workflows/       # CI/CD automation
│   ├── signature.sh         # Signs .xbps files using GitHub Secrets
│   ├── autogen-index.sh     # Generates index.html for directory browsing
│   └── autogen-json.sh      # Generates packages.json for the web frontend
├── <arch>/                  # Binary folders (x86_64, i686, aarch64, armv6l, armv7l)
│   ├── *.xbps               # Compiled binary packages
│   ├── *.xbps.sig           # Cryptographic signature (generated by CI)
│   ├── *.xbps.sig2          # Secondary signature (generated by CI)
│   ├── index.html           # Auto-generated directory listing
│   └── packages.json        # Auto-generated metadata for script.js
├── pkg-recipe/              # xbps-src build templates
│   └── <package_name>/
│       └── template
├── tools/
│   └── auto.sh              # Local automation script (Build & Copy)
├── vdocs/                   # Documentation (EN/ID)
├── index.html               # Root directory listing (Auto-generated)
└── README.md
```

## 2. Prerequisites

Before contributing, ensure you have:
1. **Void Linux** (or a compatible environment with `xbps-src` installed).
2. **Git** and **GitHub CLI (`gh`)** installed and authenticated.
3. **Write/Owner access** to the `T4n-Labs` GitHub organization repositories.

## 3. Local Development Workflow (`tools/auto.sh`)

To speed up the packaging process, we provide `tools/auto.sh`. This script handles environment setup, multi-architecture building, and file organization.

### A. Setup Environment
If you haven't cloned the `void-packages` build system yet, the script will do it for you and run the initial bootstrap.
```bash
./tools/auto.sh --setup
# Note: Running --build or --copy will also auto-setup if void-packages is missing.
```

### B. Build Packages
The script reads the `archs` variable from your template to determine which architectures to build.
```bash
./tools/auto.sh --build
# Prompts for package name -> Reads pkg-recipe/<name>/template -> Runs xbps-src
```

### C. Copy Binaries to Repository
After building, move the compiled `.xbps` files from the build environment to the correct architecture folders in this repository.
```bash
./tools/auto.sh --copy
# Prompts for source path (Default: void-packages/hostdir/binpkgs)
# Automatically parses the architecture from the filename (e.g., zvc-1.0_1.x86_64.xbps -> x86_64/)
```

## 4. Creating a New Package

Every package requires a build template located in `pkg-recipe/<package_name>/template`.

**Example Template (`pkg-recipe/zvc/template`):**
```bash
pkgname=zvc
version=1.0_1
revision=1
archs="x86_64 i686 aarch64 armv6l armv7l"
short_desc="Void package compiler — build xbps from template"
maintainer="T4n Labs <admin@t4n.org>"
license="MIT"
homepage="https://github.com/T4n-Labs/zvc"
distfiles="https://github.com/T4n-Labs/zvc/archive/v${version%_*}.tar.gz"
checksum=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

do_build() {
    make
}

do_install() {
    make DESTDIR=$DESTDIR install
}
```
💡 **Tip:** The `archs` variable is strictly parsed by `auto.sh`. Ensure it is correctly formatted (space-separated).

## 5. CI/CD Pipeline (GitHub Actions)

When you push changes to the `main` branch, GitHub Actions automatically triggers the following workflows:

1. **`signature.sh`**: 
   - Reads the `SIGN_KEY` from GitHub Repository Secrets.
   - Signs all `.xbps` files using `xbps-rindex`, generating `.sig` and `.sig2` files.
2. **`autogen-index.sh`**: 
   - Generates a clean `index.html` at the root and inside each architecture folder for easy directory browsing via GitHub Pages.
3. **`autogen-json.sh`**: 
   - Scans the `.xbps` files and templates to generate `packages.json` in each architecture folder. This file is the primary data source for the web frontend.

## 6. Frontend Integration (`script.js`)

The T4n OS web package search engine (`script.js`) relies on the generated `packages.json` files to display packages **without hitting GitHub API rate limits**.

### Data Loading Strategy
1. **Primary Source**: Fetches `<arch>/packages.json` for all architectures in parallel (`Promise.allSettled`). If one fails, it is ignored; as long as one succeeds, it proceeds.
2. **Fallback Mechanism**: If NO `packages.json` files are found, it falls back to the **GitHub Trees API** to parse `.xbps` filenames directly from the repository. 
   - ⚠️ *Warning*: The GitHub API is strictly rate-limited to **60 requests/hour/IP**. A `403` error will display a rate-limit warning to the user. A `404` is treated as an empty repository, not an error.

### Required `packages.json` Schema
The `autogen-json.sh` script generates this file, but if you are creating it manually or debugging, it **must** follow this exact structure (either as a direct array or wrapped in a `packages` object):

```json
{
  "packages": [
    {
      "name": "zvc",
      "version": "1.0_1",
      "arch": "x86_64",
      "filename": "zvc-1.0_1.x86_64.xbps",
      "size": 184320,
      "desc": "Void package compiler — build xbps from template"
    }
  ]
}
```
*Note: `name`, `version`, and `arch` are strictly required. `size` and `desc` (mapped from `short_desc`) are optional but highly recommended for the UI.*

## 7. Security & Secrets Management

To sign packages, the CI/CD pipeline requires a PEM-encoded RSA private key.

### Generating the Key (One-time setup)
```bash
ssh-keygen -t rsa -b 4096 -m PEM -f private.pem -N ""
```

### Adding to GitHub Secrets
Use the GitHub CLI to securely inject the key into the repository:
```bash
gh secret set SIGN_KEY -R T4n-Labs/repo-glibc < private.pem
```

⚠️ **CRITICAL SECURITY WARNINGS:**
- **NEVER** commit `private.pem` to the repository.
- Ensure `private.pem` is explicitly listed in your `.gitignore`.
- The public key (`private.pem.pub`) can be safely committed to a `keys/` directory for users to download and verify signatures.
- The public key metadata is also automatically embedded into the `repodata` by `xbps-rindex`.

## 8. Deployment Checklist

Follow this checklist when adding a new package to the repository:

- [ ] Created `pkg-recipe/<name>/template` with correct `archs` and metadata.
- [ ] Ran `./tools/auto.sh --build` to build the package.
- [ ] Ran `./tools/auto.sh --copy` to copy binaries to the correct arch folders.
- [ ] Committed changes: `git add . && git commit -m "feat: add <name> <version>"`
- [ ] Pushed to GitHub: `git push`
- [ ] Verified GitHub Actions completed successfully (Check the "Actions" tab).
- [ ] Verified the package appears on the web search engine and is installable via `xbps-install`.
